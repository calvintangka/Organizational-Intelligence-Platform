## 1. Verdict

**Verdict: READY_WITH_DESIGN_CHANGES.**

The repository can support a deterministic, multi-year developer-demo dataset without live AI and without changing mature organizations. The production trust engine is reusable as the source of truth, the main historical resources fit the existing migration-package model, migration verification is already organization-scoped, and server-authority cutover is bound to a verified batch.

Three gaps must be resolved before persistence work begins:

1. The migration import path currently writes `actorId: null` for `ValidationRecord`, `MemoryChangeRecord`, and `TicketRecord`, even though PostgreSQL has actor columns. TODO-025B must extend the shared types, migration projections, import, and verification to preserve optional actor IDs. This is a narrow migration-contract change, not a domain redesign.
2. `TrustEvidence` is not a migration resource and its production writer currently represents only the idempotency claim `trust_update_only -> HUMAN_REUSE`. It cannot faithfully represent every trust-changing event. The approved seed-only direct writer remains necessary, but it must be specific to this organization and this model.
3. Approximately 10,000 `TrustEvidence` rows are not semantically coherent with approximately 5,000 tickets under the current one-row-per-distinct `(organization, knowledge, source ticket, trust event type)` `HUMAN_REUSE` contract unless tickets are artificially reused across knowledge items. V1 should target approximately **4,200-4,800** genuine evidence rows. If 10,000 is non-negotiable, increase the eligible ticket/evidence-pair volume or explicitly schedule a separate TrustEvidence semantics project; do not fabricate rows in TODO-025.

None of these gaps triggers a stop condition. Trust can be generated by production logic, coherent history can be represented, isolation can be guaranteed with the controls below, and the scale is plausible subject to a dry-run package-size and import-duration gate.

## 2. Verified Production Contracts

Classification meanings:

- `REUSE_DIRECTLY`: call the existing exported contract as-is with deterministic input.
- `REUSE_WITH_SEED_WRAPPER`: keep the production shape/logic but inject the clock, IDs, ownership, or deterministic ordering outside the production function.
- `SIMULATE_WITH_PRODUCTION_PURE_FUNCTION`: use the production pure function while building history in memory; do not invoke its normal persistence/UI path per historical event.
- `GENERATE_AS_DERIVED_DATA`: calculate the record from primary simulated events/snapshots.
- `SEED_ONLY_DIRECT_PERSISTENCE`: narrow, guarded database write because migration/production lifecycle cannot preserve the required historical representation.
- `DO_NOT_USE`: unsuitable for deterministic historical generation.

Verified schema observations that affect the design:

- Lessons, versions, examples, learning history, provenance, and validation summaries are embedded in `KnowledgeItem.content`; they are not separate PostgreSQL tables.
- Candidate-to-validation and validation-to-memory uniqueness are database-enforced, but most cross-record references are strings without foreign keys.
- `ValidationRecord.actorId`, `MemoryChangeRecord.actorId`, and `TicketRecord.actorId` are optional database columns without `User` relations.
- Migration currently forces all three actor IDs to `null`; this must change before TODO-025D.
- `TrustEvidence` has an organization relation and uniqueness key but no foreign keys to knowledge, tickets, validations, or users. All such integrity is generator/verifier responsibility.
- Migration verification deliberately allows extra target rows. The developer-demo preflight/final verifier must be stricter and require an empty target before first seed and no unexpected rows afterward.

## 3. Generator Architecture

The generator is an offline, deterministic simulator that produces an immutable logical dataset and package. It does not impersonate 1,800 HTTP validation requests and does not write during simulation.

```text
checked-in config + narrative arcs + seed + code version
                         |
                         v
             deterministic clock/RNG/IDs
                         |
                         v
                 ordered domain events
                         |
                         v
       production pure lifecycle simulation in memory
                         |
             +-----------+-----------+
             |                       |
             v                       v
     primary resource snapshot   seed evidence plan
             |                       |
             v                       |
     package + stable digests         |
             |                       |
             v                       |
       offline integrity gate         |
             |                       |
             v                       |
       migration import/verify -------+
                         |
                         v
       exact-org TrustEvidence insert
                         |
                         v
      DB integrity + trust reconstruction
                         |
                         v
             server-authority cutover
```

Responsibilities A-Q:

| Area | Responsibility |
|---|---|
| A. Configuration | Profile-independent simulator settings plus separate `demo`/future `load` profile. No organization ID is inferred from environment. |
| B. RNG | Named xoshiro128** substreams derived from a fixed UTF-8 seed with SHA-256. No global mutable RNG. |
| C. IDs | Namespace-aware deterministic factories and stable ordinal allocation after global event sort. |
| D. Organization | Exact profile, brand, supported domains, thresholds, creation time, and isolation constants. |
| E. Actors | Eight deterministic fictional users, credentials, memberships, activity weights, and role capabilities. |
| F. Narrative arcs | Checked-in semantic definitions that describe problems and multi-year milestones. |
| G. Event simulation | Creates a stable chronological ledger with incident clusters, seasons, quiet periods, and dependencies. |
| H. Knowledge lifecycle | Applies canonical, version, lesson, merge, alias, validation, and pattern transitions. |
| I. Trust | Calls production `recordResolution`; never accepts a configured final score. |
| J. Tickets | Generates deterministic ticket text, classifications, outcomes, actors, references, and parseable IDs. |
| K. Provenance/evidence | Derives candidates, validations, memory changes, examples, logs, and the separate TrustEvidence insert plan. |
| L. Metrics | Reduces primary events/records into `OrgMetrics`; no authored dashboard totals. |
| M. Package | Sorts supported resources, counts them, constructs fixed metadata, and uses production digest helpers. |
| N. TrustEvidence | Validates and inserts only exact seed evidence rows with explicit IDs/timestamps after migration verification. |
| O. Verification | Runs offline and post-database invariants, trust-chain replay, metric recomputation, and exact row-set checks. |
| P. Runner | Dry-run by default; create-only persistence mode; checkpointed intake/import/evidence/verify/cutover. |
| Q. Reset/reseed | Separate exact-ID destructive command with allowlist, denylist, confirmation phrase, and snapshot/digest checks. |

## 5. Determinism Contract

### Fixed inputs

- Generator profile: `demo`.
- Organization ID: `profile-oip-developer-demo`.
- Default seed string: `oip-developer-demo-v1`.
- RNG algorithm version: `xoshiro128ss-v1`.
- History start: `2023-01-01T00:00:00.000Z`.
- History anchor/end: `2026-06-30T23:59:59.000Z`.
- Time zone for business-calendar decisions: `Asia/Jakarta`; all stored timestamps are UTC ISO strings.
- Template/content version: explicit integer in config, initially `1`.
- Code version: Git commit recorded in the generated manifest, but not injected into logical resource content unless the user intentionally wants new digests for a code change.

The determinism identity is:

```text
canonical config bytes + seed + generator contract version + narrative content version
```

### RNG

Use xoshiro128** with four unsigned 32-bit words. Derive each stream state from SHA-256 of:

```text
oip-demo|rng-v1|<seed>|<stream-name>
```

Examples of stream names are `volume/auth-sso-loop`, `time/auth-sso-loop`, `actor/validation`, and `outcome/billing-duplicate-charge`. Named substreams prevent the addition of one arc from perturbing unrelated arcs. Use unsigned 32-bit operations, rejection sampling for bounded integers, fixed decimal rounding, and never sort with a random comparator.

### IDs

IDs are content-independent stable namespace plus deterministic ordinal/slug:

- actors: `user-oip-demo-01` through `user-oip-demo-08`
- knowledge: `demo-ki-<arc-slug>`
- lessons: `demo-les-<arc-slug>-<nnn>`
- candidates: `demo-cand-<event-ordinal-6>`
- validations: `demo-val-<event-ordinal-6>`
- memory changes: `demo-mcr-<event-ordinal-6>`
- evidence: `demo-te-<evidence-ordinal-7>`
- versions: `<knowledge-id>-v<nnn>`
- patterns: `demo-pat-<arc-slug>`
- logs: `demo-log-<event-ordinal-7>`
- learning history: `demo-hist-<event-ordinal-7>`
- migration metadata uses production-generated batch IDs; those IDs are operational metadata, not logical dataset IDs.

Ticket IDs use the production formatter and must parse through `parseTicketId`:

```text
OIP-<ticket-created-date-YYYYMMDD>-<global-sequence-padded-to-4-or-more>
```

Sequence numbers are global within this organization from 1 through 5,000. `TicketSequence.counter` is 5,000.

### Ordering and timestamps

1. Generate semantic event intents per arc using named RNG streams.
2. Sort by `(timestamp, event-priority, arc-id, per-arc-ordinal)`.
3. Allocate global event ordinals and dependent IDs only after this sort.
4. Sort every package resource explicitly: knowledge/candidates/validations/memory/patterns/logs by ID, tickets by parsed sequence, and embedded versions/lessons/history/examples by `(createdAt, id)`.
5. Resolve timestamp collisions by deterministic millisecond offsets within the parent event. Do not depend on array insertion timing.

### Actor, arc, volume, validation, and trust selection

- Actor assignment uses role-filtered weighted sampling from named streams. Eligibility is checked before sampling.
- Arc selection is not random over independent records. The configured arc receives a deterministic annual/seasonal intensity curve and incident windows.
- Monthly ticket targets use largest-remainder allocation after deterministic seasonal weights, so totals equal the configured target exactly.
- Within a month, business-day weighted slots are allocated first; weekends receive a lower configured probability except incident windows.
- Validation batching is deterministic by `(knowledge, review-window, outcome-kind)`. Source-ticket IDs are stable sorted arrays.
- Trust events are selected from configured outcome probabilities but always executed by production `recordResolution`. No score is an input.

### Known determinism hazards and treatment

| Hazard | Treatment |
|---|---|
| `Date.now()` / `new Date()` defaults | Never call without an injected simulated timestamp in generator code. Wrap production functions that embed wall-clock IDs. |
| `Math.random()` | Forbidden by lint/probe in generator paths. |
| cuid/UUID/database defaults | Supply IDs for logical seed records. Operational migration batch IDs and internal `TicketRecord.id` may differ without changing package/resource projections. |
| `@updatedAt` | Exclude operational timestamps from logical digest/reconstruction. Supply historical domain timestamps explicitly where schema allows. |
| unordered maps/sets/object construction | Normalize keys via production `stableStringify`; sort arrays explicitly before digesting. |
| locale-sensitive sort | Use ASCII IDs and a fixed comparator; avoid environment-sensitive human-text collation. |
| floating point | Use integer basis points/weights during allocation; round only at specified projection boundaries. |
| live LLM | Prohibited. Use pre-authored arc content and deterministic templates. |
| embeddings/semantic services | Prohibited in V1 generation. Retrieval QA may run later, but its output cannot alter seed data. |
| password salts | Use fixed development-only salts derived from actor IDs; do not call random-salt `hashPassword` for synthetic actors. |
| compression/JSON formatting | Digests use canonical `stableStringify`, not file whitespace or gzip bytes. |

Same inputs must produce identical logical resources, resource counts, event manifest, package/resource digests, and TrustEvidence plan. Database operational metadata is allowed to differ and is not seed truth.

| Category | Volume | Age/maturity | Evolution |
|---|---:|---|---|

## 7. Historical Event Model

The simulator ledger is immutable and contains at least:

```ts
interface HistoricalEvent {
  id: string;
  type:
    | "organization_created" | "actor_available" | "ticket_created"
    | "pattern_detected" | "candidate_created" | "validation"
    | "knowledge_created" | "lesson_discovered" | "lesson_reinforced"
    | "lesson_alias_created" | "knowledge_merged" | "version_created"
    | "human_reuse" | "automatic_success" | "edited_resolution"
    | "wrong_resolution" | "ticket_closed";
  at: string;
  arcId?: string;
  actorId?: string;
  ticketIds: string[];
  knowledgeId?: string;
  candidateId?: string;
  validationId?: string;
  memoryChangeId?: string;
  payload: Record<string, unknown>;
}
```

Event rules:

- `ticket_created` is primary. All dependent records reference already-created tickets.
- `pattern_detected` is derived only for unmatched tickets before canonical creation or for genuinely emerging variants.
- Every candidate has exactly one later validation; V1 approved history may include a small rejected-candidate sample, but rejected candidates do not mutate knowledge and therefore need a clarified memory policy before inclusion. Default V1 uses approved candidates for all 1,800 candidate/validation/memory chains.
- A `validation` creates the `ValidationRecord` and `MemoryChangeRecord` projection atomically in simulation. Their timestamps may be equal, matching the production transaction.
- A `knowledge_created` event uses `createCanonicalProblem`; creation trust is 20 and is not a TrustEvidence event.
- Lesson events construct/merge lessons through production lesson identity functions.
- `version_created` updates a parent template/guidance and creates a new embedded version. A lesson-only change does not create a version.
- Resolution events call `recordResolution` and produce counters/trust changes. They are then wrapped in a `trust_update_only` candidate/validation/memory chain for historical audit compatibility.
- `knowledge_merged` means supporting evidence merged into an existing canonical item, not two mature trust histories combined by taking a maximum.

## 8. Trust Evolution Model

Production constants in `lib/trustEngine.ts` are authoritative:

- initial trust: 20
- successful human reuse: +5
- successful automatic resolution: +3
- required human edits: additional -2
- wrong answer: -10
- clamp: integer 0-100
- recommend threshold: 40
- demo auto threshold: 80 unless the final profile decision changes it

| Historical event | Production call | Requested raw delta | Records | Idempotency |
|---|---|---:|---|---|
| knowledge created | `createCanonicalProblem` / `withLearningDefaults` | initial 20, not a delta | candidate, approved validation, memory change, knowledge v1 | Candidate and validation IDs deterministic; create is not TrustEvidence-guarded. |
| successful human reuse | `recordResolution({mode:"human", success:true})` | +5 | ticket(s), candidate, validation, memory change, knowledge; `HUMAN_REUSE` evidence for eligible source pairs | Production uniqueness prevents the same source ticket/knowledge/event type from contributing twice. Multi-source validation applies the delta once, not once per evidence row. |
| successful automatic resolution | `recordResolution({mode:"automatic", success:true})` | +3 | ticket(s), candidate, validation, memory change, knowledge | Current production persistence labels every `trust_update_only` claim as `HUMAN_REUSE`; TrustEvidence therefore does not faithfully distinguish this event. Do not fabricate an `AUTO_SUCCESS` evidence taxonomy in TODO-025A. |
| edited successful human resolution | `recordResolution({mode:"human", success:true, requiredEdits:true})` | +3 (+5-2) | ticket, candidate, validation, memory change, knowledge | Current TrustEvidence can claim reuse but does not separately represent the edit penalty. |
| wrong resolution | `recordResolution({mode, success:false})` | -10 (or -12 with edit) | ticket, candidate, validation, memory change, knowledge | No production TrustEvidence representation for the negative event. |
| canonical support merge without resolution | `mergeIntoCanonicalProblem` | 0 | candidate, validation, memory change, knowledge examples/counters | Candidate uniqueness and source/reference verification only. |
| version created | deterministic version wrapper | 0 unless accompanied by an explicitly scheduled resolution outcome | candidate, validation linked to version, memory change, knowledge | Version ID unique inside the package and chronologically ordered. |
| lesson created/merged/aliased | lesson production functions | 0 unless accompanied by an explicit resolution outcome | candidate, validation, memory change, knowledge | Content fingerprint and alias invariants enforce idempotency. |

Configured maturity affects the **number, timing, and mix of events**, never `trustScore`. If an arc expected to be mature finishes at 77 because of its event history, the stored score is 77. Tuning requires changing the event plan and regenerating; no post-hoc score correction is allowed.

### Trust reconstruction algorithm

For each knowledge item:

1. Load its memory changes sorted by `(timestamp, id)` and locate the single creation record with `beforeState = null`.
2. Confirm the creation `afterState.trustScore` equals production initial trust.
3. For every next record, deep-compare its normalized `beforeState` with the prior record's `afterState` for all learning/trust fields. The final imported knowledge row is allowed to add only persistence revision metadata; its domain projection must equal the last `afterState`.
4. Correlate the memory record to the deterministic manifest event and its candidate/validation/source tickets.
5. Re-run `recordResolution` on the reconstructed pre-event item for trust-affecting events, with the stored historical timestamp, mode, success, edit flag, organization profile, and validations available as of that time.
6. Compare produced `trustFrom`, `trustTo`, applied delta, counters, success rate, eligibility, and timestamps against the memory `afterState`.
7. For non-trust events, require trust equality before/after.
8. Compare the last reconstructed state with the stored `KnowledgeItem` trust/counters and independently check TrustEvidence only for event types the current model genuinely represents.

The manifest is an input to verification because the current database records do not encode automatic-vs-human-vs-wrong outcome semantics sufficiently to replay trust from PostgreSQL alone. This is a current architecture limitation, not permission to infer deltas from the stored after-score.

## 18. Reset/Reseed Safety Design

Allowlist:

```text
profile-oip-developer-demo
```

Mandatory denylist:

```text
profile-maesa-tech
profile-fastdrop-logistics
profile-pramana-legal
test-oip-regression
Maesa Tech
FastDrop Logistics
Pramana Legal
```

Also reject any target not byte-for-byte equal to the allowlist, any case/whitespace-normalized near match, empty value, wildcard, prefix, environment default, or inferred active organization.

Required invocation shape for the future reset command:

```text
--organization profile-oip-developer-demo
--confirm RESET-profile-oip-developer-demo
--expected-current-package-digest <sha256>
--reason <non-empty operator reason>
```

The command prints a read-only exact row-count/digest preview, then requires a second interactive entry of the full confirmation phrase unless a narrowly controlled CI recovery mode supplies an equivalent one-time token. `--yes`, environment-only target selection, or active-workspace selection are insufficient.

`resetOrganizationData` is not suitable because it leaves migration batches and server authority, and cutover is one-way to its existing batch. Correct reseed recovery is an exact-ID transaction/orchestration that deletes the demo `Organization` row (cascading its memberships, business records, evidence, migration metadata, and authority), preserves global synthetic users, recreates the foundation/memberships, then executes a fresh create-only seed. Before deletion, write a recoverable package/verification snapshot outside PostgreSQL and verify its digest.

The generic `/reset` and organization `DELETE` HTTP routes must not be used by this script. No reset is implemented or executed in TODO-025A.

## 21. Risks and Current Architecture Limitations

| Risk/limitation | Impact | Required control |
|---|---|---|
| Migration nulls actor IDs | Synthetic behavior cannot be verified from persisted refs | TODO-025B shared type/import/verification extension. |
| TrustEvidence only covers current reuse idempotency | Cannot be a complete trust ledger | Memory-chain + manifest replay is authoritative; evidence target reduced. |

| Database lacks many cross-resource FKs | Orphans are structurally possible | Comprehensive offline and DB verifier. |

V1 scale is not yet clearly unsafe, but it is not proven safe. Package-size and import-duration gates are mandatory before D. This is a measured risk, not a stop condition.
